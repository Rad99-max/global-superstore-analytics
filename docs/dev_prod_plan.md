# План разделения DEV/PROD

Дата: 10.11.2026. Статус: предложение, НЕ реализовано.

В этом этапе изменяется только документация. Подключений к PostgreSQL, запуска
pipeline, изменения ролей, баз, SQL, Python, .env и Power BI не выполнялось.
Общая архитектура описана в [README](../README.ru.md#архитектура); описание внедрённой
BI-роли — в [powerbi_reader.md](powerbi_reader.md). Этот документ описывает
только будущий переход сред и не дублирует архитектуру хранилища.

## 1. Проверенное исходное состояние

Основания: чтение файлов проекта 10.11.2026, предыдущий read-only аудит БД и
подтверждение пользователем внедрения роли 09.11.2026. Текущий каталог БД
на этом этапе повторно не запрашивался.

| Компонент | Состояние |
|---|---|
| .env.dev | localhost:5432 / sales_dwh / postgres |
| .env.prod | localhost:5432 / sales_dwh / postgres |
| Выбор профиля | .env.local: USE_PROD_ENV=1; код принимает только 0 или 1 |
| PIPELINE_ENV | Есть в профилях, но не используется кодом для выбора среды |
| Конфигурация | .env + выбранный профиль; переменные процесса не переопределяют файлы |
| Запуск ETL | run_pipeline.py в корне, модули pipeline/config.py и pipeline/load_raw.py |
| Слои | raw → staging → dwh → mart; это схемы внутри одной базы |
| Power BI | Один PBIP, 11 PostgreSQL-источников с фиксированным localhost:5432/sales_dwh |
| BI-аутентификация | powerbi_reader; успешный refresh подтверждён пользователем |
| ETL-аутентификация | Пока postgres; отдельные ETL-роли не внедрены |

Пароли не проверяются выводом и не включаются в план.

SQL-файлы создания подтверждают схемы raw, staging, dwh, mart. Ранее аудит БД
также обнаружил public. Новые базы и схемы в этом этапе не создавались.

### Ограничения, которые нельзя обойти заменой .env

- pipeline/config.py разрешает только POSTGRES_DB=sales_dwh.
- Проверки current_database()/sales_dwh есть также в run_pipeline.py,
  pipeline/load_raw.py, загрузочных SQL и SQL настройки/проверки reader-роли.
- Pipeline закреплён за APPROVED_LOAD_ID и исходным snapshot; SQL_STAGES
  проверяются на тот же UUID. Это отдельный контракт, не переключатель среды.
- run_pipeline.py выполняет этапы последовательно. Транзакции принадлежат
  отдельным SQL-файлам; единой атомарной транзакции всего pipeline нет.
  Успех RAW не означает успех DWH/MART.
- В модель входят четыре DWH dimensions и семь MART. Зависимости MART от
  DWH фактов остаются внутри соответствующей базы, без связей DEV → PROD.
- Изменение роли в Power BI не изменяет сервер/базу и не разделяет среды.

## 2. Минимальная целевая схема

Чтобы не переносить уже проверенный PROD и не менять действующий endpoint:

| Назначение | DEV | PROD |
|---|---|---|
| База | sales_dwh_dev — новая | sales_dwh — действующая |
| Схемы | raw, staging, dwh, mart | Существующие схемы |
| ETL-роль | sales_etl_dev — новая | sales_etl_prod — новая |
| BI-роль | powerbi_reader_dev — новая | powerbi_reader — уже внедрена |
| Администрирование/DDL | postgres | postgres |
| Использование | Разработка, проверки, тестовый refresh | Только принятые версии |

Две отдельные базы на одном PostgreSQL instance дают независимые данные,
схемы и права. Это не физическая изоляция CPU, диска или администратора:
postgres сохраняет административный доступ к обеим базам.

Переименование рабочей базы в sales_dwh_prod не требуется для изоляции и
не входит в минимальный переход. Это отдельное необязательное решение.

### Роли и права

- postgres выполняет создание баз, расширений, схем, объектов и выдачу прав.
  Приложения после перехода не используют superuser.
- Каждая ETL-роль получает только необходимые права в своей базе:
  чтение/запись таблиц, COPY FROM и доступ к конкретным sequences;
  DELETE/TRUNCATE — только там, где они действительно нужны загрузочным SQL.
  Без SUPERUSER, CREATEDB, CREATEROLE и владения рабочими объектами.
- Создание структуры отделяется от регулярного запуска ETL. Набор прав
  подтверждается тестом всего pipeline под соответствующей ETL-ролью,
  включая журналы, обработку пропуска/сбоя и проверку собственных сессий.
- BI-роли получают CONNECT, USAGE dwh/mart и SELECT на тот же явный набор
  11 источников. Без DML и постоянного DDL; sequences им не нужны.
- BI-роли не включаются в другие роли. Принятые исключения PUBLIC TEMPORARY
  и public USAGE сохраняются; это не даёт SELECT на таблицы другой среды.
- Роли PostgreSQL общие для instance, поэтому имена DEV/PROD различаются.
  Не выдавать DEV-роли права на PROD и наоборот. PUBLIC CONNECT может
  разрешать само подключение к другой базе, но не чтение её прикладных таблиц.
  Запрет даже на подключение потребует отдельного решения по PUBLIC/HBA.
- Владение текущими PROD-объектами в минимальном этапе не меняется. Owner-роли
  без LOGIN можно рассмотреть позже как самостоятельную доработку.

## 3. Поэтапный переход и условия продолжения

### Этап A — зафиксировать восстановимую исходную точку

После отдельного согласования реализации:
1. Зафиксировать проверенную версию кода/PBIP и состояние SQL-схем.
2. Снять согласованный резервный снимок sales_dwh в native/custom формате,
   сохранить его вне Git с ограниченным доступом.
3. Зафиксировать источник Excel, его SHA-256, SUCCESS load_id, контрольные суммы
   и количества на уровнях RAW/STAGING/DWH/MART, состояние sequences,
   расширения и кодировку.
4. Отдельно сохранить перечень необходимых ролей/прав и рабочие настройки
   подключения, без паролей и password verifiers в документации/репозитории.
5. Согласовать окно работ и порядок возврата. До проверенного backup не
   изменять PROD. Возможность восстановления проверить до выпуска изменений.

Готовность: есть проверенная копия для восстановления и исходные KPI.

### Этап B — адаптировать выбор среды сначала вне PROD

Отдельная будущая правка Python/SQL:
1. Ввести единый явный выбор DEV/PROD для запуска и согласованный маппинг
   profile → server/database/ETL role. Предпочтительно явный параметр запуска;
   отсутствие или противоречие параметров должно останавливать запуск.
2. Не использовать одновременно независимые USE_PROD_ENV и PIPELINE_ENV.
   Выбрать один механизм, описать миграцию текущих профилей и запусков.
3. Заменить жёсткое разрешение одной базы на проверку точного ожидаемого
   назначения среды во всех перечисленных местах. Не удалять safety checks.
4. До первой записи проверить фактические current_database(), роль и endpoint.
   DEV не должен продолжать работу при назначении на PROD. PROD-запуск —
   отдельное явное действие после принятия проверок, без автоматического fallback.
5. Сохранить snapshot-contract: не заменять фиксированные load_id и SHA-256
   ради прохождения проверок. Если нужны новые snapshots, это отдельная задача.
6. Адаптировать security SQL к имени DEV-базы и DEV-reader-роли, сохранив
   ту же политику и allowlist. Текущие скрипты жёстко привязаны к sales_dwh
   и powerbi_reader, поэтому запускать их на DEV без адаптации нельзя.

Готовность: негативные тесты маршрутизации проходят без записи не в ту базу.

### Этап C — создать и наполнить DEV

После отдельного разрешения операций:
1. Создать sales_dwh_dev и её роли; расширения/структуру готовит администратор.
2. Восстановить полный согласованный снимок, а не только MART: нужны RAW-журнал,
   staging, dimensions, facts, ключи, FK и исходный snapshot.
3. Не копировать PROD-ACL и владельцев автоматически: восстановление с
   no-owner/no-privileges, затем явная выдача DEV-прав. Это не позволит случайно
   дать powerbi_reader доступ к DEV или DEV-ETL доступ к PROD.
4. Проверить значения sequences, PK/FK, типы/точность, source SHA-256,
   SUCCESS load_id и соответствие APPROVED_LOAD_ID.
5. Сначала сверить восстановленное состояние, затем отдельно проверить полный
   ETL в DEV, повторный запуск/пропуск того же источника и обработку ошибки.
6. Подтвердить, что при всех этих действиях исходная PROD-база не меняется.

Готовность: DEV воспроизводится и проходит DQ/reconciliation под DEV-ролью.

### Этап D — изолировать разработку Power BI

1. Сохранить одну версионируемую логику модели/отчёта; не вести две вручную
   расходящиеся копии DAX.
2. В будущем добавить параметры сервера/базы для всех 11 источников.
   Рабочая разработка и её тестовый экземпляр должны указывать на DEV,
   утверждённый PROD-артефакт — на sales_dwh.
3. Для DEV указать отдельную сохранённую credential powerbi_reader_dev.
   Учётные данные не становятся параметром TMDL/PBIP и не копируются в Git.
4. Проверить реальный refresh и все страницы/фильтры/Insights в DEV.
5. Прежде чем сохранять или reload PBIP, соблюдать guarded-write: перед записью и сразу после неё проверять, что в Desktop нет несохранённых изменений (`hasUnsavedChanges=false`).
   Для записи PROD-артефакта также нужна проверенная и сохранённая Desktop-сессия.
6. Power BI Service/workspaces не являются обязательным условием этого
   локального перехода; их возможное подключение — отдельный этап.

Готовность: разработка читает DEV, действующий PROD-отчёт сохраняет проверенный
источник и reader-подключение.

### Этап E — принятие версии и выпуск

1. Принять код/SQL/модель только после DEV QA; зафиксировать версию релиза.
2. Не заменять PROD полным dump из изменяемого DEV. Продвигать проверенную
   версию кода/схем и согласованный исходный snapshot.
3. Перед любыми PROD-записями обновить backup и контрольную точку отката.
4. Структурные изменения выполняет администратор, загрузку — sales_etl_prod.
5. При сбое любого этапа ETL остановить выпуск. Не публиковать частично
   обновлённые MART и не выполнять финальный Power BI refresh до общего PASS.
6. Проверить права существующего powerbi_reader после любых изменений объектов.
7. Только после успешной сверки выполнить PROD refresh и визуальную приёмку.

CI/CD не внедряется этим планом. Для портфельного проекта достаточно ручных,
зафиксированных контрольных шагов до появления реальной необходимости
автоматизировать выпуск.

## 4. Обязательный набор проверок

- Разные фактические имена баз и раздельные app-роли; отрицательные проверки
  доступа DEV-учётной записи к прикладным данным/записи PROD и наоборот.
- Все уровни и sequences восстановлены, нет потери/дублирования business keys.
- Counts, SUM(Sales/Profit), Orders, Quantity, Returns и reconciliation всех MART
  согласованы с тем же исходным snapshot. Числа сравнивать до форматного округления.
- Pipeline проходит полностью и повторно на DEV; ошибка останавливает этапы,
  не разрешая выдавать частичный результат за успешный выпуск.
- Reader SELECT на 11 источниках, запрет постоянного DML/DDL, согласованные
  PUBLIC-исключения; ETL не выполняется под BI-ролью.
- Реальный Power BI refresh, Year/Quarter/Month, Market/Region/Country,
  PY/YoY, multi-year, empty/PY-unavailable, interactions, tooltip и Insights.
- Контроль Market Performance за 2014: Sales 3 405 746,45 USD,
  Profit 406 935,23 USD, Margin 11,95%, Net Loss −121,38K USD,
  Active Countries 143. Сравнить с принятым состоянием за 2015 и иными контекстами.
- Restore проверенного backup и возврат к предыдущему PBIP действительно возможны.

## 5. Откат

До изменения PROD сохранить рабочую версию кода/PBIP, настройки маршрутизации,
права и проверенный backup. Пароли не экспортировать в репозиторий.

- Сбой только в DEV: остановить DEV; PROD продолжает работать. Восстановить
  DEV из проверенной копии, не направлять DEV pipeline на PROD.
- Сбой модели/источника без изменения PROD-данных: вернуть предыдущий
  PROD-артефакт и его параметры, затем проверить refresh/контрольные KPI.
- Сбой после PROD-загрузки: остановить ETL/refresh, в согласованном окне
  восстановить sales_dwh из проверенного предрелизного backup и вернуть
  совместимую версию кода/PBIP. Учесть сессии подключения, роли и grants.
  Не маскировать ошибку произвольным повторным запуском pipeline.
- После восстановления проверить права reader, целостность, reconciliation,
  KPI и визуализации; только затем возобновлять обычную работу.

Точки прекращения перехода: нет проверенного backup/restore, неверная база
или роль, не проходит snapshot-contract, не сходятся totals/ключи или refresh.
При любом из этих условий PROD не переключать и не продолжать выпуск.

## 6. Что требует отдельного согласования

Создание DEV-базы/ролей, права новых ETL-ролей, изменения Python/SQL/.env,
параметризация и записи Power BI, реальные pipeline/refresh/restore и выпуск.
Ни одно из этих действий не выполнено в задаче документирования.
