## Согласованные исключения PUBLIC (09.11.2026)

Пользователь согласовал сохранение существующих прав PUBLIC:
- TEMPORARY на sales_dwh.
- USAGE на схему public.

Ни один из двух SQL-файлов не меняет права PUBLIC. CONNECT через PUBLIC — это
тоже обычный существующий доступ к базе, а не новое право для других рабочих
ролей.

PostgreSQL объединяет прямые, унаследованные и PUBLIC-права; NOINHERIT не
отнимает права PUBLIC. Прежняя строгая блокирующая проверка preflight снята
только для этих двух исключений. Политика применена 09.11.2026, как
подтверждено выше. Любой повторный запуск или изменение политики по-прежнему
требует отдельного разрешения.

Действующая политика доступа к данным приложения:
- Явные CONNECT, USAGE на dwh/mart и SELECT ровно на одиннадцать источников.
- Нет INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER/MAINTAIN, в том числе
  на уровне столбцов; нет доступа к последовательностям и права передачи прав
  (grant option).
- Нет CREATE DATABASE/schema и CREATE в постоянных схемах, включая public.
  Нет постоянного владения объектами и пути через членство в ролях или
  SET ROLE, который позволил бы выполнить DROP.
- Нет фактического SELECT на отношения приложения вне списка разрешённых.
- Нет доступных пользовательских функций SECURITY DEFINER.
- Нет массовых прав и прав на будущие таблицы.

Роль reader может создавать, изменять и удалять свои временные объекты. Это
НЕ утверждение, что запрещены любые команды CREATE/DROP. Проверки владения
исключают временные отношения и объекты временного пространства имён (типы,
функции) в этой базе, но не постоянные объекты и не владение в других базах.
Владение временными объектами не даёт прав на изменение постоянных
аналитических таблиц.

Остающиеся риски и ограничения:
- TEMPORARY позволяет расходовать ресурсы и место на диске. Настройки сеанса
  «только чтение» по умолчанию — лишь дополнительная защита; пользователь может
  их сбросить. Квоты и глобальные настройки не менялись.
- USAGE на public открывает функции, которые PUBLIC может выполнять.
  Проверенные функции pgcrypto не являются SECURITY DEFINER; их права EXECUTE
  не менялись. Новые функции и изменения ACL требуют новой проверки. При
  последующих проверках скрипты отклоняют доступные функции приложения с
  SECURITY DEFINER.
- Обращаться к аналитическим объектам с указанием схемы. Подготовленный
  search_path по умолчанию явно ставит pg_temp последним, чтобы временная схема
  неявно не получала приоритет. Настройка search_path не является границей
  авторизации.
- Другие базы могут независимо давать PUBLIC право CONNECT. Это не изоляция баз
  на уровне всего кластера. Доступ к каталогу и системным функциям остаётся
  обычным.
- Мониторинг дрейфа прав не установлен. Проверку нужно повторять после
  изменений ролей, PUBLIC, ACL по умолчанию или схем. Аудит не нашёл прав PUBLIC
  на отношения, столбцы и последовательности приложения и записей ACL по
  умолчанию.

REVOKE FROM PUBLIC, изменения владения, членства, глобальных настроек и ACL по
умолчанию не входят в настройку. Существующие рабочие роли, определения таблиц
и данные не затрагиваются.

## Справка по настройке — повторный запуск только после подтверждения

Роль уже развёрнута. Команды ниже сохранены как справка для эксплуатации, а не
как указание пересоздать роль или повторить настройку сейчас. Любой будущий
запуск требует отдельного согласования.

Команда администратора, из корня репозитория:

~~~powershell
psql -X -h localhost -p 5432 -U postgres -d sales_dwh -W -v ON_ERROR_STOP=1 -f sql/06_security/01_prepare_powerbi_reader.sql
~~~

Используйте psql, а не графический клиент, который продолжает работу после
ошибок. Транзакция и ON_ERROR_STOP исключают частичное применение; при ошибке
отключитесь, чтобы откатить открытую транзакцию. Выдача прав и настройки
идемпотентны. Новая роль остаётся NOLOGIN.

Для уже существующей роли reader к откату приводят: небезопасные атрибуты,
владение объектами, пути через членство или SET ROLE, подчинённые члены роли,
постоянные права на запись или DDL, права передачи прав, неожиданный доступ
SELECT или к схемам вне двух исключений, доступ к последовательностям или
доступные пользовательские функции SECURITY DEFINER. Скрипт не исправляет
автоматически уже существующую рабочую роль. Даже подчинённое членство
отклоняется, чтобы новые права не могли косвенно изменить доступ другой
рабочей роли.

Если разрешённая таблица удалена и создана заново, права нужно заново
проверить и выдать. Новые источники модели требуют проверенного изменения
списка разрешённых. Скрипт не меняет владельцев схем и таблиц, бизнес-логику
и существующие данные.

## Пароль и включение LOGIN — вручную, после согласования

После успешной настройки откройте отдельный интерактивный сеанс psql:

~~~powershell
psql -X -h localhost -p 5432 -U postgres -d sales_dwh -W
~~~

Введите следующие команды вручную:

~~~text
SET password_encryption = 'scram-sha-256';
\password powerbi_reader
ALTER ROLE powerbi_reader LOGIN;
~~~

Вводите пароль только в скрытом запросе. Никогда не указывайте пароль в
литерале ALTER ROLE, аргументе командной строки, URI, PGPASSWORD, в файле .env,
закоммиченном в Git, в чате, на скриншоте, в записи сеанса, в файле
репозитория или в журнале CI.

Команда psql \password шифрует пароль на стороне клиента, поэтому пароль в
открытом виде не попадает в историю SQL-команд и в журналы SQL на сервере.
Verifier тоже является чувствительными данными: перед установкой пароля
проверьте правила записи терминала и аудита. В этих артефактах нет ни пароля,
ни verifier.

Не включайте LOGIN после неудачной проверки preflight. Повторный запуск
сохраняет существующее состояние LOGIN и пароля; он не меняет и не сбрасывает
рабочие учётные данные.

## Проверка — реальный вход под powerbi_reader после согласования и включения

~~~powershell
psql -X -h localhost -p 5432 -U powerbi_reader -d sales_dwh -W -v ON_ERROR_STOP=1 -f sql/06_security/02_verify_powerbi_reader.sql
~~~

Проверке нужен НАСТОЯЩИЙ сеанс powerbi_reader; SET ROLE от администратора
отклоняется. Она выполняется в BEGIN READ ONLY и проверяет:

1. Аутентификацию, CONNECT, правильные базу и пользователя.
2. SELECT * LIMIT 0 для всех одиннадцати источников Power BI (реальная проверка
   прав и метаданных, а не только просмотр ACL в каталоге).
3. Отсутствие прав INSERT, UPDATE, DELETE и связанных прав на запись и
   обслуживание на уровне таблиц и столбцов, включая права, унаследованные
   через PUBLIC и роли.
4. Отсутствие CREATE в базе и постоянных схемах, прав передачи прав и доступа к
   последовательностям. TEMPORARY на sales_dwh и USAGE на public — принятые
   исключения.
5. Отсутствие постоянного владения объектами и членства, позволяющих повысить
   права через DROP или SET ROLE. Принятое владение временными объектами эту
   проверку не проваливает.
6. Отсутствие доступных пользовательских функций SECURITY DEFINER, дающих
   обходной путь.
7. Контрольный запрос по географии за 2015 год. Текущие ожидаемые итоги —
   примерно Sales 4 299 865,87 и Profit 504 165,97.

Постоянные CREATE/DROP проверяются через пути авторизации, без создания или
удаления реального аналитического объекта. У DROP нет отдельного бита права в
ACL. CREATE/DROP временных объектов, принадлежащих reader, — принятое
исключение. Функции проверки прав смотрят реальные фактические права, поэтому
READ ONLY не скрывает случайно выданное право на запись.

Живой проверки отказа INSERT/UPDATE/DELETE/CREATE/DROP нет: даже откатываемая
проба может запустить триггеры на уровне команды, сдвинуть последовательности
или взять блокировки DDL. Если нужны буквальные проверки отказа операций,
получите отдельное согласование на одноразовые тестовые объекты. Не используйте
рабочие аналитические таблицы как цели разрушающих тестов.

Контрольный запрос носит информационный характер и не является неизменным
утверждением о наборе данных, который может обоснованно измениться позже.
Результаты запросов не сохраняются.
