GLOBAL SUPERSTORE — MART EXECUTIVE OVERVIEW: ПРОЕКТ ДИЗАЙНА

1. НАЗНАЧЕНИЕ И GRAIN

Бизнес-вопрос: «Как развивается бизнес и насколько качественным является этот рост
с точки зрения прибыльности?»
Целевая таблица: mart.executive_monthly.
Grain: одна строка на один календарный месяц по Order Date, глобально по всему бизнесу.
month_date — первое число месяца, тип DATE; это метка периода, а не день совершения всех продаж.
Таблица не имеет Customer/Product/Geography/Discount/Returns grain.
Для текущего опубликованного DWH ожидается 48 строк: 2012-01-01..2015-12-01.
Не добавлять январь 2016 только из-за наличия Ship Date в календаре DWH.

2. ПОЛЯ И КЛЮЧ

поле | PostgreSQL тип | обязательность | определение
month_date | DATE | NOT NULL, PRIMARY KEY | первое число месяца Order Date
sales | NUMERIC без (p,s) | NOT NULL | сумма fact_order.total_sales за месяц
profit | NUMERIC без (p,s) | NOT NULL | сумма fact_order.total_profit за месяц
orders | BIGINT | NOT NULL | количество заказов за месяц
unprofitable_orders | BIGINT | NOT NULL | количество заказов с total_profit < 0

Пяти полей достаточно. Surrogate month key не нужен: month_date однозначно задаёт grain.
Year, Quarter, Month, month name и sort columns в MART не дублировать.
Не хранить margin, rate, YoY, PY, изменения в п.п., insight-status или готовый текст выводов.
Не добавлять служебные поля на этом шаге: контракт содержит только пять указанных полей.
Технические сведения публикации остаются задачей будущего процесса обновления.
Будущая реализация контролирует первый день месяца, уникальность month_date,
orders >= 0 и 0 <= unprofitable_orders <= orders. Отрицательный Profit допустим.
NUMERIC не округлять при построении; денежный формат отчёта отделён от хранения.

3. ИСТОЧНИК И ПРАВИЛА ПОСТРОЕНИЯ

Единственный источник мер: dwh.fact_order.
Order Date разрешается через fact_order.order_date_key -> dwh.dim_date.date_key.
Из calendar_date определяется календарный месяц. Ship Date не используется.
Order = (order_id, customer_id), техническая идентификация через order_key;
поэтому Orders — COUNT строк fact_order, а не COUNT(DISTINCT order_id).
Не присоединять fact_order_line или fact_return_signal: это не требуется для мер
и может размножить суммы заказов. People не используется.

Sales = сумма total_sales; Profit = сумма total_profit.
Orders = количество заказов; Unprofitable Orders = число total_profit < 0.
Классифицировать по полному Profit КАЖДОГО заказа до месячной агрегации.
Не считать убыточные товарные строки и не классифицировать все заказы по Profit месяца.
total_profit = 0 — Break-even: входит в Orders, не входит в Unprofitable Orders.
Не применять ROUND или epsilon при классификации: используется утверждённый NUMERIC Profit.
Sales/Profit не пересчитывать из скидок/Shipping Cost и не уменьшать по Returns.

Обновление читает один согласованный опубликованный снимок DWH. Для текущего этапа:
SUCCESS load_id f44edd71-d712-4fa0-81d3-98ad24e00599.
Не суммировать версии одного набора данных; lineage проверяется через DWH/raw.load_log.
Для маленького месячного MART достаточно будущей атомарной полной пересборки публикации,
с сохранением одной строки на month_date. Сейчас загрузчик не создаётся.

Месячное покрытие: непрерывная сетка от первого до последнего месяца Order Date.
Месяц без заказов внутри подтверждённого покрытия получает четыре нулевых показателя.
Это не правило превращать отсутствующую/неполную загрузку или NULL мер заказа в ноль:
такие случаи должны остановить публикацию и потребовать DQ-решения.
Месяцы за пределами покрытия не добавляются как месяцы с нулевыми продажами.
Для текущих данных все 48 месяцев имеют заказы; NULL total_sales/total_profit нет.

4. ПРОВЕРЕННЫЕ КОНТРОЛЬНЫЕ ИТОГИ ТЕКУЩЕГО DWH

Проверка выполнена только на чтение в sales_dwh.
Order Date: 2012-01-01..2015-12-31; месяцы: 2012-01..2015-12, всего 48.
SUM(sales) = 12642501.90988000002174815.
SUM(profit) = 1467457.2912799999311949806.
SUM(orders) = 25 739.
SUM(unprofitable_orders) = 6 309.
Break-even orders = 163; это проверочное число, отдельное поле MART не требуется.
Остальные 19 267 заказов имеют положительный Profit.
Месячные итоги должны независимо совпадать с DWH, а их суммы — с итогами выше.

5. POWER BI: СВЯЗЬ С КАЛЕНДАРЁМ

Рекомендуется простой Import model: месячный MART плюс отдельная ежедневная таблица дат,
источником которой служит существующая dwh.dim_date.
Связь: DimDate[calendar_date] (1) -> ExecutiveMonthly[month_date] (*), активная,
направление фильтрации только DimDate -> MART. Обе колонки имеют тип Date.
Кардинальность задать явно: уникальность month_date в текущем MART не требует 1:1
и двунаправленной фильтрации. Не связывать повторяющийся MonthStart ежедневного календаря
с MART через many-to-many; не связывать month_date с surrogate integer date_key.

month_date сопоставляется ровно с первым днём месяца в календаре.
Year/Quarter/Month фильтруют набор ежедневных дат, включающий первые числа нужных месяцев.
Поэтому эти slicers корректно фильтруют месячные суммы. Эта связь не распределяет их по дням.
Все slicers, оси и PY-фильтры берутся из DimDate, не из скрытого поля даты факта.
Визуальная иерархия: Year -> Quarter -> YearMonth; дневной/недельный drill-down отключён.
Не предлагать диапазоны отдельных дней, MTD, сравнение неполных месяцев или Ship Date:
месячный MART не содержит информации для таких расчётов.

Состояние DWH-календаря: 2012-01-01..2016-01-07, 1 468 дней.
2016 год неполный: его начало присутствует для отгрузок. Импорт всех этих строк как
готового полного годового календаря для classic time intelligence не рекомендуется.
Решение для этой страницы: в Power Query импортировать из dim_date только полные годы,
покрывающие месячный MART: 2012-01-01..2015-12-31, 1 461 ежедневная строка.
При следующем обновлении границы определять по годам покрытия MART; до публикации
проверять полноту каждого импортируемого года. В DWH ничего не менять.
Если будущий год не полностью представлен в dim_date, отдельным шагом согласовать
дополнение календаря в Power BI или расширение DWH; не скрывать проблему пропусками дат.

Для выбранного простого варианта использовать classic date-column time intelligence:
пометить DimDate как Date table по calendar_date; даты уникальны, без NULL и разрывов.
Отключить Auto date/time для этой модели, чтобы не создавать конкурирующие календари.
calendar_year и calendar_quarter уже есть в dim_date; calendar_month задаёт порядок месяцев.
Подписи Quarter, MonthName, YearMonth и их sort columns можно получить в Power BI
из атрибутов этой dimension; это не дополнительные поля MART.
YearMonth сортируется хронологически (например, по Year*100+Month), а не по алфавиту.

6. СЕМАНТИЧЕСКИЕ МЕРЫ: KPI COVERAGE

Ниже определения будущих DAX measures, не готовая реализация DAX.
Sales = SUM(sales); Profit = SUM(profit); Orders = SUM(orders).
Unprofitable Orders = SUM(unprofitable_orders).
Profit Margin = DIVIDE(Profit, Sales), доля, отображается как процент.
Unprofitable Order Rate = DIVIDE(Unprofitable Orders, Orders), доля.
На квартале/годе/общем итоге сначала суммировать числители и знаменатели.
Нельзя усреднять месячные margin/rate: это даёт неверные невзвешенные итоги.

PY — та же мера в календарном контексте, сдвинутом на год назад через DimDate[calendar_date]
(например, SAMEPERIODLASTYEAR). Не применять time intelligence к month_date MART.
YoY Sales/Profit/Orders = (текущее значение - PY) / PY.
При отсутствии PY или нулевом PY вернуть BLANK, не 0 и не бесконечность.
Profit Margin delta, п.п. = (Profit Margin - Profit Margin PY) * 100.
Unprofitable Order Rate delta, п.п. = (Rate - Rate PY) * 100.
Для delta проверять наличие ОБОИХ периодов; BLANK PY не трактовать как нулевую долю.
Разница долей 0.20 - 0.18 = 2.0 п.п.; это не относительный рост на 2%.

KPI | достаточно пяти полей | правило
Sales и Sales YoY | да | сумма Sales, сравнение того же периода PY
Profit и Profit YoY | да | сумма Profit, сравнение того же периода PY
Profit Margin и delta PY, п.п. | да | отношение сумм, разность долей
Orders и Orders YoY | да | сумма monthly Orders, а не количество строк MART
Unprofitable Order Rate и delta PY, п.п. | да | отношение сумм двух счётчиков

2012 год не имеет PY в источнике: YoY и delta PY для него BLANK/N/A.
Фильтр Year=2013 должен позволять PY measure обращаться к 2012 через календарь.
Не отрезать PY-данные на этапе импорта только потому, что они не выбраны slicer.
На multi-year totals сравнивать тот же набор месяцев год назад только при наличии
полного сопоставимого PY-покрытия; иначе BLANK, без незаметного сравнения разных длительностей.
Для первой версии ограничить временной выбор полными месяцами и непрерывными периодами.
Проверить месячный, квартальный и годовой контексты, а также первый год без PY.

7. VISUAL COVERAGE И BUSINESS INSIGHTS

Sales & Profit Trend | месячная ось YearMonth из DimDate; две меры сумм
Profit Margin Trend | та же ось; отношение Profit/Sales в каждом месяце
Unprofitable Order Rate Trend | та же ось; Unprofitable Orders/Orders в каждом месяце
KPI cards | текущий выбранный период, PY и соответствующее изменение
Business Insights: Growth | Sales/Orders/Profit YoY и их согласованность
Business Insights: Margin | текущая маржа и delta PY в п.п.; рост Sales при снижении маржи
Business Insights: Risk | текущая доля убыточных заказов и delta PY в п.п.

Достаточность: все запрошенные visuals и описательные Insights поддерживаются.
Правила будущих текстовых Insights: направление Growth определяется знаком YoY;
снижение Margin и рост Unprofitable Order Rate означают ухудшение соответствующего
аспекта качества роста. При отсутствии сопоставимого PY показывать «нет сравнения».
Не вводить произвольные пороги «высокого риска», сводный score или причинные объяснения.
Рост доли убыточных заказов не равен доказанному будущему убытку и не объясняет его причины.
Для причин по Geography/Product/Customer/Discount потребуется другой grain и другой MART.
Нельзя присоединять эти dimensions к глобальному месячному итогу и считать его фильтруемым.

8. ОГРАНИЧЕНИЯ И КРИТЕРИИ ПРИЁМКИ БУДУЩЕЙ РЕАЛИЗАЦИИ

Проверить ровно 48 уникальных первых чисел месяцев и отсутствие разрывов покрытия.
Проверить все месячные суммы/счётчики и общие контрольные итоги; отсутствие fan-out.
Проверить Break-even, отрицательный Profit, нулевые знаменатели и отсутствие PY.
Проверить отношения сумм на квартале/годе, а не средние месячных процентов.
Проверить Year/Quarter slicers и PY для 2013, 2014, 2015 на полном дневном календаре.
Проверить, что дневные фильтры/оси не показывают месячный итог как дневные продажи.
В будущем частичный последний месяц должен быть явно обозначен/исключён из сравнения;
эта таблица не позволяет восстановить сравнимый MTD из одной месячной строки.
Максимальная дата заказа сама по себе не доказывает полноту будущей поставки.
Публикация не должна маскировать ошибки загрузки нулевыми месяцами.

При отрицательном Profit PY стандартный процент YoY может быть контринтуитивным:
отмечать смену знака/убыток и показывать абсолютную разницу в DAX/tooltip;
не объявлять «улучшение» только по положительному проценту и не менять формулу молча.
Пороговые статусы и специальные правила отрицательной базы требуют отдельного согласования.
Денежная валюта в источнике не установлена; знак конкретной валюты не назначать.
Power BI не гарантирует сохранение произвольной точности PostgreSQL NUMERIC:
Decimal Number использует приблизительную арифметику; Fixed Decimal ограничивает шкалу 4.
Не выбирать Fixed Decimal только ради денежного формата: в источнике есть более точные суммы.
При реализации проверить mapping connector и расхождения на младших разрядах; DWH/MART
остаются точным контрольным источником. Unprofitable Orders классифицируется в PostgreSQL,
а не повторно по округлённому/конвертированному в Power BI Profit.

9. ИСТОЧНИКИ РЕКОМЕНДАЦИЙ POWER BI

Microsoft: календарь для time intelligence должен иметь уникальные непустые ежедневные даты,
без разрывов и с полными годами; classic-вариант требует Mark as date table:
https://learn.microsoft.com/en-us/power-bi/guidance/model-date-tables
Microsoft: факт с grain выше дня можно связать с календарём по первому дню периода;
анализ на более низком временном grain требует ограничения мер:
https://learn.microsoft.com/en-us/power-bi/guidance/relationships-many-to-many#relate-higher-grain-time-periods
Сдвиг контекста на предыдущий год:
https://learn.microsoft.com/en-us/dax/sameperiodlastyear-function-dax
Обработка нулевого знаменателя через DIVIDE:
https://learn.microsoft.com/en-us/dax/best-practices/dax-divide-function-operator
Ограничения числовых типов семантической модели:
https://learn.microsoft.com/en-us/power-bi/connect-data/desktop-data-types

Рекомендация проекта: сохранить минимальный пятиколоночный MART и вычислять сравнения,
доли и Insights в семантическом слое. Проверки календаря обязательны до сборки страницы.
На этом шаге создан только данный документ; SQL, Power BI и PostgreSQL не изменялись.
