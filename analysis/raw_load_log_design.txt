GLOBAL SUPERSTORE: проект журнала загрузок RAW
Дата: 2026-10-16
Статус документа: архитектурное предложение; реализация не выполнялась.

1. Название и границы ответственности

Рекомендуемая таблица: raw.load_log.
Одна запись соответствует одной попытке обработать один исходный Excel-файл целиком: Orders, Returns и People. У всех строк трёх листов, записанных этой попыткой, одинаковый _load_id, равный load_log.load_id.
Схема raw подходит: журнал описывает поступление данных именно в RAW. Отдельная схема метаданных и дополнительные таблицы для текущего масштаба не нужны.
Это журнал попыток, а не каталог уникальных файлов. Один SHA-256 может встречаться в нескольких записях журнала, но иметь не более одной успешной загрузки.

2. Минимальный состав: 10 полей

load_id UUID — PRIMARY KEY, следовательно NOT NULL. Новый UUID на каждую попытку; повтор после FAILED не переиспользует старый идентификатор.
source_file TEXT — NOT NULL, непустой путь/имя фактически обрабатываемого файла. Для текущего источника: data/source/global_superstore_2016.xlsx. Это происхождение, а не ключ идемпотентности.
source_sha256 TEXT — допускает NULL до получения хеша или при ошибке чтения файла. После получения хранится SHA-256 точных байтов файла: 64 шестнадцатеричных символа нижнего регистра. Для SUCCESS и SKIPPED обязателен.
started_at TIMESTAMPTZ — NOT NULL, фактический момент регистрации попытки до чтения/хеширования Excel.
finished_at TIMESTAMPTZ — NULL у STARTED, обязателен для конечных статусов.
status TEXT — NOT NULL, один из STARTED, SUCCESS, FAILED, SKIPPED. Технический CHECK по этим значениям оправдан; отдельный PostgreSQL ENUM не нужен.
orders_rows_loaded BIGINT — NOT NULL, начальное значение 0, неотрицательное число зафиксированных строк raw.orders данной попытки.
returns_rows_loaded BIGINT — NOT NULL, начальное значение 0, то же для raw.returns.
people_rows_loaded BIGINT — NOT NULL, начальное значение 0, то же для raw.people.
error_text TEXT — NULL у STARTED, SUCCESS и SKIPPED; непустой текст у FAILED. Должен включать этап и причину ошибки, а при несовпадении объёмов — лист и ожидаемое/фактическое число строк. Не записывать пароли и секреты подключения.

BIGINT для счётчиков даёт запас и соответствует естественному результату подсчёта строк PostgreSQL. Ограничивать их текущими 51 290 / 1 079 / 24 нельзя: это размеры конкретной поставки, а не контракт будущих файлов.
TEXT для хеша выбран вместо CHAR(64), чтобы не вводить семантику дополнения пробелами. Контроль длины и алфавита здесь технический, в отличие от ограничений на исходные бизнес-значения.

3. Семантика счётчиков и диагностика неполной загрузки

Счётчики означают строки, действительно зафиксированные в RAW, а не число прочитанных, отправленных в INSERT или обработанных до исключения.
В выбранной модели все три листа записываются атомарно. Поэтому у STARTED, FAILED и SKIPPED счётчики равны 0. У SUCCESS они равны фактическим количествам строк в трёх RAW-таблицах по соответствующему _load_id.
Ноль при STARTED означает отсутствие зафиксированных строк, а не отсутствие выполняемой работы. Ноль при FAILED означает откат всей попытки, даже если часть строк была вставлена внутри незавершённой транзакции.
Перед записью прочитать все три обязательных листа и определить ожидаемое количество исходных записей в каждом. После вставки сверить эти количества с фактическим числом RAW-строк по load_id для каждого листа. Отсутствие листа или любое несовпадение — FAILED с откатом всех трёх таблиц.
В сообщении такой ошибки сохранить, например: этап проверки объёма; Orders: ожидалось X, внутри транзакции записано Y; транзакция отменена, зафиксировано 0. Эти диагностические Y не переносить в счётчики загруженных строк.
Не принимать SUCCESS только потому, что исключения не возникло. Проверить все листы и все три количества; исключить молчаливый пропуск строк парсером. Подсчёт строк не доказывает неизменность содержимого: загрузчик также должен сохранять исходные значения согласно утверждённой RAW-схеме.
Для минимального журнала отдельные expected_rows, read_rows и attempted_rows не обязательны: сверка выполняется загрузчиком, а расхождение сохраняется в error_text. При аварийном завершении процесса до записи ошибки промежуточные количества могут быть утрачены; это осознанное ограничение минимальной модели. Успех при этом не фиксируется.
Если позднее потребуется систематически анализировать ожидаемые объёмы даже для аварийных попыток, можно добавить три nullable-поля ожидаемых количеств. Сейчас они не входят в рекомендуемый минимум.

4. Жизненный цикл и границы транзакций

STARTED → SUCCESS
1) После допуска к запуску создать новую запись STARTED с новым load_id, временем начала и тремя нулевыми счётчиками. Зафиксировать её отдельной короткой транзакцией, чтобы последующий откат RAW не уничтожил след попытки.
2) Прочитать неизменяемый набор байтов файла, вычислить SHA-256 и сохранить хеш в журнале. Именно эти байты использовать для чтения Excel: не хешировать одну версию файла, а затем перечитывать уже изменившийся путь.
3) Проверить повторы, прочитать все обязательные листы, определить ожидаемые количества и проверить возможность сохранения значений без бизнес-преобразований.
4) В одной транзакции записать Orders, Returns и People с одним _load_id. Проверить количества по _load_id и подготовить итоговые счётчики.
5) В ЭТОЙ ЖЕ транзакции обновить журнал до SUCCESS, записать счётчики и finished_at. Только затем зафиксировать транзакцию. Таким образом RAW и SUCCESS становятся видимыми совместно.

STARTED → FAILED
При ошибке чтения, отсутствующем листе, ошибке вставки или проверки откатить транзакцию RAW целиком. После отката отдельной короткой транзакцией записать FAILED, finished_at, нулевые счётчики и error_text. Если файл не удалось прочитать и хеш неизвестен, source_sha256 остаётся NULL.

STARTED → SKIPPED
Если этот SHA-256 уже имеет SUCCESS, не вставлять строки RAW. Завершить новую запись статусом SKIPPED, временем окончания и нулевыми счётчиками. error_text остаётся NULL: это штатный контролируемый пропуск. В минимальной модели SKIPPED имеет единственное значение — файл уже успешно загружен.

SUCCESS, FAILED и SKIPPED — конечные состояния. Обычный повторный запуск создаёт новую запись, а не возвращает конечную запись в STARTED. Журнал не перезаписывает историю неудач.

5. Повторные запуски и идемпотентность

Тот же SHA-256 после SUCCESS: новая попытка → SKIPPED; новых RAW-строк нет. Это действует и при другом имени/пути файла: байтово одинаковый файл не является новой поставкой.
Тот же SHA-256 после FAILED, без SUCCESS: новая попытка с новым load_id допускается; прежняя FAILED сохраняется. При корректной атомарной модели у неё нет зафиксированных RAW-строк, поэтому очищать или дедуплицировать исходные записи не требуется.
Тот же путь с другим SHA-256: это другая байтовая версия источника, которая может быть загружена под новым load_id. Нельзя молча заменять или удалять старую успешную версию. Возможное пересечение бизнес-записей разных версий не устраняется в RAW; выбор версии для последующих слоёв — отдельное решение.
Байтово разные XLSX могут содержать одни и те же бизнес-значения. SHA-256 предотвращает повторную загрузку одинаковых байтов, а не семантическую дедупликацию таблиц.
Принудительная повторная загрузка уже успешного SHA-256 в текущий контракт не входит. Если она понадобится, правила переобработки и публикации версий нужно согласовать отдельно, а не отключать защиту скрытым флагом.

6. Конкурентные запуски и аварии

Для масштаба проекта достаточно одного одновременно работающего загрузчика. Практический механизм — одна общая session-level advisory lock PostgreSQL для RAW-pipeline, удерживаемая на выделенном соединении между транзакциями до конечного статуса.
Получить блокировку до регистрации STARTED и проверки SHA-256; второй процесс ждёт допуска, затем регистрирует собственную попытку и повторно проверяет журнал. Ожидание допуска не является зарегистрированной попыткой чтения файла; started_at обозначает начало допущенной попытки. При обрыве сессии session-level lock освобождается PostgreSQL.
Предполагается, что все экземпляры pipeline соблюдают одну и ту же блокировку. Проверки SUCCESS в приложении без сериализации недостаточно: два процесса могут одновременно решить, что файла ещё нет.
В качестве небольшой дополнительной защиты на уровне БД рекомендуется частичный уникальный индекс по source_sha256 только среди записей со статусом SUCCESS. Он допускает много FAILED/SKIPPED для одного файла, но запрещает второй SUCCESS. Это предложение индекса, не SQL DDL. При конфликте транзакция RAW откатывается; после проверки уже существующего SUCCESS попытка может завершиться SKIPPED.
Не вводить глобальный UNIQUE на source_sha256: он запретил бы историю повторов после ошибок и журналирование пропусков.
Если процесс завершился аварийно, запись может остаться STARTED. Отсутствие finished_at означает незавершённую/неподтверждённую попытку, а не SUCCESS. Один только возраст записи не доказывает зависание живого процесса.
После получения общей блокировки и подтверждения отсутствия прежнего владельца проверить оставшиеся STARTED. При соблюдении атомарной модели для них не должно быть зафиксированных RAW-строк. Такие прерванные попытки завершить FAILED с пояснением об аварийном прекращении; затем разрешить новый load_id. finished_at в этом случае — время фиксации результата восстановления, фактический момент аварии неизвестен.
Если у STARTED найдены зафиксированные RAW-строки, это нарушение выбранного протокола. Остановить повторную загрузку и провести сверку; не удалять строки автоматически и не объявлять успех только по совпадению количества.
При потере соединения во время COMMIT результат может быть неизвестен клиенту. После восстановления сначала прочитать журнал: SUCCESS означает, что и RAW уже зафиксирован. Не переписывать такую запись в FAILED из-за сетевого исключения и не повторять вставки вслепую.
Если сама БД недоступна, гарантировать запись ошибки в неё невозможно: остаётся STARTED, который обрабатывается восстановлением. Отдельная система мониторинга/heartbeat для этого проекта не предлагается.

7. Ограничения, оправданные технической логикой

PRIMARY KEY: load_id. Обязательны load_id, source_file, started_at, status и три счётчика.
source_file — непустое значение; source_sha256, если задан, — 64 символа из 0–9 и a–f.
status — только STARTED, SUCCESS, FAILED, SKIPPED.
Каждый счётчик неотрицателен. Для всех статусов, кроме SUCCESS, каждый счётчик равен 0.
У STARTED finished_at отсутствует; у конечных статусов присутствует. Если finished_at задан, он не раньше started_at. При будущей реализации использовать фактическое время завершения, а не время начала длинной транзакции.
Для SUCCESS и SKIPPED source_sha256 обязателен.
Для FAILED error_text обязателен и непуст; для остальных статусов — NULL.
Для SUCCESS счётчики не обязаны быть положительными: пустой, но существующий и корректно обработанный лист технически возможен. Критерий — соответствие прочитанному источнику, а не текущим фиксированным размерам.
Частичная уникальность успешного source_sha256 оправдана выбранной политикой идемпотентности.
Порядок переходов статусов и сверка счётчиков с другими таблицами обеспечиваются протоколом загрузчика. Обычный CHECK проверяет состояние строки, но не историю переходов и не фактические количества в RAW. Триггеры для этих проверок на данном этапе избыточны.

8. Связь с утверждёнными техническими полями RAW

В каждой из raw.orders, raw.returns и raw.people поле _load_id UUID должно ссылаться на raw.load_log.load_id; для будущей реализации рекомендуется NOT NULL и FOREIGN KEY без каскадного удаления. Это техническая связь происхождения, а не бизнес-связь листов.
Все строки одной попытки получают один load_id. Физические строки находят по _load_id, а внутри источника — по _source_file, _source_sheet и _source_row_number. _raw_id остаётся независимым surrogate key.
Индексы по _load_id на трёх RAW-таблицах полезны для сверки количеств и диагностики; внешний ключ сам по себе не создаёт такие индексы на стороне RAW.
_loaded_at TIMESTAMPTZ обозначает время записи строки; started_at/finished_at описывают попытку целиком. Эти времена не обязаны совпадать.
_source_file TEXT в RAW должен соответствовать source_file журнала; _source_sheet содержит Orders, Returns или People; _source_row_number INTEGER — физический номер строки Excel. Новых бизнес-ограничений на эти листы этот документ не вводит.
Утверждённое уточнение: исходное поле Row ID в raw.orders имеет тип INTEGER. Оно не заменяет _raw_id BIGINT и не связано с ключом журнала. Предыдущий анализ Orders здесь не редактировался.

9. Что сейчас не нужно

Не нужны отдельные таблицы файлов/листов/этапов, JSONB-метаданные, номера повторов, worker_id, heartbeat, три статуса по листам, сохранённая длительность и суммарный счётчик. Длительность и сумму можно вычислить из имеющихся полей.
Не нужны UNIQUE по пути, фиксированные размеры листов, ограничения на бизнес-ключи и автоматическое удаление RAW при повторе. Связь с предыдущей успешной попыткой для SKIPPED находится по SHA-256; отдельный skipped_load_id для минимума не обязателен.
Ограничение минимальной модели: она не хранит детальный прогресс выполнения и точную точку аварии, если процесс не успел записать ошибку. Для диагностики обычных ошибок и защиты от публикации частичного файла достаточно атомарной загрузки, трёх счётчиков, статуса и error_text.

10. Проверенные технические основания

Предложенная архитектура — проектное решение для данного pipeline. Возможности PostgreSQL сверены по официальной документации:
- Атомарность транзакций: https://www.postgresql.org/docs/18/tutorial-transactions.html
- Session-level advisory locks и их жизненный цикл: https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS
- Частичный уникальный индекс, ограничивающий только успешные записи: https://www.postgresql.org/docs/18/indexes-partial.html
В PostgreSQL не выполнялись подключения, запросы или изменения. SQL DDL и Python-код не создавались. Единственный добавленный файл — analysis/raw_load_log_design.txt.

11. Рекомендуемая структура raw.load_log

поле | PostgreSQL тип | ограничения | назначение
load_id | UUID | PRIMARY KEY, NOT NULL | Уникальный идентификатор одной попытки; значение для _load_id во всех трёх RAW-таблицах.
source_file | TEXT | NOT NULL; непустое значение | Путь/имя фактически обрабатываемого исходного Excel-файла.
source_sha256 | TEXT | NULL до вычисления/при ранней ошибке; иначе 64 lowercase hex; NOT NULL для SUCCESS/SKIPPED; частичная уникальность среди SUCCESS | Контроль версии байтов файла и предотвращение повторной успешной загрузки.
started_at | TIMESTAMPTZ | NOT NULL | Момент регистрации допущенной попытки перед чтением файла.
finished_at | TIMESTAMPTZ | NULL только для STARTED; обязателен для конечных статусов; не раньше started_at | Момент завершения попытки или регистрации результата аварийного восстановления.
status | TEXT | NOT NULL; CHECK по STARTED, SUCCESS, FAILED, SKIPPED | Текущее состояние попытки; конечные состояния не переиспользуются для нового запуска.
orders_rows_loaded | BIGINT | NOT NULL; начальное значение 0; >= 0; 0 при статусе, отличном от SUCCESS | Число зафиксированных строк raw.orders с данным _load_id.
returns_rows_loaded | BIGINT | NOT NULL; начальное значение 0; >= 0; 0 при статусе, отличном от SUCCESS | Число зафиксированных строк raw.returns с данным _load_id.
people_rows_loaded | BIGINT | NOT NULL; начальное значение 0; >= 0; 0 при статусе, отличном от SUCCESS | Число зафиксированных строк raw.people с данным _load_id.
error_text | TEXT | Непустое значение обязательно для FAILED; NULL для остальных статусов | Этап и причина сбоя, включая ожидаемые/фактические количества при неполной загрузке.
