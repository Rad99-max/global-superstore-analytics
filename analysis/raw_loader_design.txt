GLOBAL SUPERSTORE — проект алгоритма SOURCE → RAW
Дата: 2026-10-16
Результат: только проектирование. Код, SQL-файлы и объекты БД не создаются и не изменяются.

Исходный файл: data/source/global_superstore_2016.xlsx.
Назначение: sales_dwh; raw.load_log, raw.orders, raw.returns, raw.people.
Модель исполнения: один экземпляр pipeline. Advisory lock, параллельные workers, отдельная система метаданных и дополнительные таблицы не нужны.

A. ПОШАГОВЫЙ АЛГОРИТМ

1. Инициализация попытки и конфигурации

Определить корень проекта относительно файлов модуля, а не текущей папки терминала. Сформировать абсолютный путь для открытия источника; в source_file и _source_file хранить одинаковый стабильный путь относительно проекта: data/source/global_superstore_2016.xlsx.
Создать новый UUID v4 load_id для каждого запуска. Не брать его из имени файла, SHA-256 или предыдущего FAILED; не использовать UUID бизнес-строк.
Прочитать настройки без вывода значений секретов: базовый .env, затем .env.local как переключатель окружения. USE_PROD_ENV=1 выбирает .env.prod; USE_PROD_ENV=0 — .env.dev. Выбранный файл перекрывает явно заданные параметры базового .env; неуказанный там пароль остаётся из .env. Не подмешивать молча переменные окружения процесса поверх этого порядка.
Для первой реализации принимать только явно распознанные 0/1; отсутствие или неверный переключатель — ошибка конфигурации. Использовать POSTGRES_HOST, POSTGRES_PORT, POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD. Не печатать конфигурационный словарь, DSN, пароль или содержимое env-файлов.
Проверить обязательные параметры. POSTGRES_DB должен быть sales_dwh. Использовать существующие настройки, не изменять env-файлы. Тайм-аут подключения ограничить, например 10 секундами.

2. Подключение и предварительная проверка базы

Открыть одно соединение psycopg 3 с autocommit=True; все группы изменяющих операций ниже выполнять только в явных транзакционных контекстах. Это позволяет коротко фиксировать журнал и не держать случайную транзакцию от диагностического SELECT.
В read-only транзакции проверить current_database() и наличие четырёх утверждённых таблиц, колонок и ключевых ограничений. Подтвердить поддержку Unicode клиентским соединением. Не выполнять DDL, не пытаться создать или автоматически исправить схему. Не требовать пустоты всех RAW-таблиц при каждом запуске: это сломает повторные запуски и историю поставок.
Если current_database() не sales_dwh — остановиться без записи в чужую базу. Если невозможно подключиться или raw.load_log недоступна, зарегистрировать попытку в БД невозможно: безопасное сообщение в консоль и ненулевой код завершения, без ложного обещания FAILED в журнале. UUID можно показать для диагностики, пароль — нельзя.
Если журнал доступен, но остальные RAW-таблицы не соответствуют контракту, зарегистрировать STARTED и затем FAILED без RAW-вставок. Никакого автоматического ремонта структуры.

3. Регистрация STARTED — отдельная короткая транзакция T1

Вставить в raw.load_log: новый load_id, source_file, started_at, status STARTED. source_sha256=NULL, finished_at=NULL, error_text=NULL, три счётчика=0. Время начала получить как фактическое время БД; не переносить время предыдущего запуска.
Зафиксировать T1 до открытия Excel. Это необходимо, чтобы ошибка отсутствующего файла тоже оставляла STARTED → FAILED, а откат RAW не уничтожал запись попытки.
Ошибка регистрации — остановка без загрузки. Не начинать RAW, если факт STARTED не подтверждён. При неопределённом исходе COMMIT T1 сначала перепроверить журнал по этому UUID; не повторять INSERT вслепую.

4. Проверка источника и единственный снимок байтов

Проверить, что путь существует и является обычным читаемым файлом. Отсутствующий файл, каталог вместо файла, отказ доступа или ошибка чтения — переход к обработке FAILED; хеш остаётся NULL.
Прочитать файл в bytes один раз. Для текущего XLSX около 8,5 МБ это простой и приемлемый вариант. Посчитать hashlib.sha256 по этим точным байтам и получить 64 lowercase hex.
Открывать книгу далее только из BytesIO этого же снимка. Не хешировать файл, а затем повторно открывать путь для загрузки: файл мог измениться между действиями. SHA-256 характеризует именно байты, переданные Excel-парсеру. Исходный XLSX никогда не сохранять из openpyxl.

5. Проверка идемпотентности — короткая транзакция T2

Сохранить вычисленный source_sha256 в текущей STARTED. По этому хешу искать записи SUCCESS, а не любые записи и не совпадение только имени файла.
Если SUCCESS найден: в T2 обновить текущую попытку до SKIPPED, установить finished_at, оставить счётчики 0 и error_text=NULL. Проверить, что изменена ровно одна запись STARTED с нашим load_id. Зафиксировать T2 и завершить запуск успешно как контролируемый пропуск. Книгу читать и строки RAW копировать уже не нужно.
Если есть только FAILED: разрешить загрузку с новым load_id, не изменять старую FAILED. Если есть SKIPPED, но нет соответствующего SUCCESS, это несогласованность истории — не считать SKIPPED доказательством успешной загрузки; остановить попытку как FAILED для проверки.
Если есть другая STARTED для того же хеша и нет SUCCESS: не запускать повторную запись вслепую. Завершить новую попытку FAILED с указанием незавершённого load_id; прежнюю запись не менять автоматически. Для восстановления нужен отдельный разбор, описанный ниже.
Если препятствий нет, зафиксировать source_sha256 и оставить статус STARTED. Наличие уникального индекса для SUCCESS не заменяет эту проверку. Параллельный запуск не поддерживается; advisory lock не добавлять.

6. Чтение и проверка трёх листов до длинной транзакции

Открыть BytesIO-снимок через openpyxl в read_only=True, data_only=False. Читать объекты ячеек, а не только values: нужны тип ячейки, номер физической строки и сведения о числовом формате.
Обязательные листы: Orders, Returns, People. Отсутствие любого — FAILED до RAW-вставок. Другие листы, если появятся, не загружать и не объединять с этими тремя.
Проверить точные заголовки первой строки: Orders — 24 исходных поля, Returns — Returned, Order ID, Region; People — Person, Region. Имена, регистр и порядок должны совпадать с утверждённым контрактом. Не делать trim, переименование, автоматическое угадывание или исправление заголовков. Неожиданные дополнительные колонки не отбрасывать молча — FAILED.
Для каждого листа последовательно пройти физические строки со 2-й до worksheet.max_row включительно. В этом алгоритме область данных определяется физическим диапазоном листа, а не количеством непустых значений в первом столбце. Не использовать pandas.index или номер успешно преобразованной записи.
Не пропускать внутренние, полностью пустые или повторяющиеся строки в этом диапазоне: они также получают запись RAW с NULL бизнес-полями и заполненными техническими полями. Если будущий файл имеет растянутый форматированием диапазон или неверные размеры, не придумывать правило удаления строк; несоответствие контракту требуется явно разобрать. Для текущего проверенного файла таких неоднозначностей нет.
Для каждого успешно прочитанного исходного ряда увеличить независимый expected_count листа и подготовить одну типизированную запись с физическим номером. Для текущего объёма можно держать подготовленные списки трёх листов в памяти. Не вести expected_count как число успешно отправленных в COPY: иначе потеря строки при подготовке могла бы остаться незамеченной.
Формулы (тип f), ошибки Excel (тип e), неизвестный тип значения или неоднозначное преобразование — FAILED с именем листа, координатой ячейки и описанием проблемы. Не брать кэшированное значение формулы: data_only=False позволяет обнаружить сам факт формулы. В текущем источнике формул и ошибок нет.
Все счётчики в журнале остаются 0: чтение и подготовка не означают зафиксированную загрузку.

7. Технические поля и физические номера строк

_source_row_number — настоящий номер строки Excel. Заголовки находятся в строке 1, поэтому первая запись имеет номер 2, а не 1 и не 0. Пропуск или повтор в бизнес-идентификаторе не влияет на этот номер.
Для текущего файла: Orders 2–51291; Returns 2–1080; People 2–25. Проверенные количества: 51 290, 1 079 и 24. Это контрольные ориентиры первой загрузки, а не жёсткие лимиты будущего pipeline. При подготовке первой загрузки отдельно сообщить, если источник уже отличается от этих ориентиров; не подгонять результат удалением строк.
_source_file — тот же проектно-относительный путь, что source_file в журнале. _source_sheet — точное имя листа. _load_id — UUID этой попытки во всех трёх таблицах.
_loaded_at — один timezone-aware момент загрузки для всех строк данной попытки, полученный из времени БД в начале транзакции RAW. Это не дата Order Date и не обязательное равенство started_at. _raw_id не передавать: его генерирует identity PostgreSQL; не копировать в него Row ID.

8. Атомарная запись SOURCE → RAW — одна транзакция T3

После завершения подготовки открыть один явный транзакционный контекст на том же соединении. Внутри проверить, что запись load_id всё ещё STARTED и хеш не изменён; получить общий _loaded_at.
Перед вставками убедиться, что в raw.orders/raw.returns/raw.people нет зафиксированных строк с этим новым _load_id. Это проверка технического происхождения, не дедупликация бизнес-полей. Не удалять найденные строки автоматически.
Загрузить последовательно Orders, Returns, People через три COPY FROM STDIN в одном T3. Указывать явный список всех бизнес-колонок в утверждённом порядке, затем пять заполняемых технических колонок. _raw_id исключить из списка COPY.
Составлять идентификаторы таблиц и столбцов через psycopg.sql.Identifier; схему raw указывать явно. Значения передавать через write_row, а не интерполировать в SQL. Не выполнять INSERT/COMMIT по строке, не использовать ON CONFLICT DO NOTHING, to_sql, очистку таблиц или промежуточные staging-таблицы.
После завершения всех трёх COPY посчитать COUNT(*) каждой таблицы только по текущему _load_id. Сравнить с тремя independently computed expected_count из этапа чтения. Для каждой исходной записи должна существовать одна вставленная строка.
Если любое количество отличается, выбросить ошибку и полностью откатить T3. Общие размеры таблиц, cursor.rowcount и размер последнего COPY-блока не заменяют эту сверку.
При полном совпадении обновить raw.load_log для нашей STARTED до SUCCESS, записать фактические три количества, finished_at, error_text=NULL. Проверить, что обновлена ровно одна строка.
Зафиксировать T3 только после этого обновления. Данные всех листов и SUCCESS фиксируются атомарно. Не делать отдельный поздний COMMIT для SUCCESS после уже зафиксированных RAW-вставок.

9. Обработка обычной ошибки — отдельная транзакция T4

Исключение при чтении, преобразовании, COPY, сверке или обновлении SUCCESS сначала должно покинуть транзакционный контекст T3, если он открыт. Контекст выполняет ROLLBACK всех трёх RAW-вставок и незавершённого изменения журнала.
После отката в новой короткой транзакции обновить свою STARTED до FAILED: finished_at обязателен, error_text непустой, три rows_loaded=0. Сохранённый хеш оставить; если получить его не удалось, допускается NULL. Проверить изменение ровно одной записи и зафиксировать T4.
Сообщение ошибки: этап, класс исключения/SQLSTATE, безопасная причина, лист, номер строки/колонки; при расхождении — expected и actual для листов. Не сохранять полный traceback с конфигурацией, DSN, пароль, строку подключения или дамп исходного ряда; PostgreSQL COPY-context может содержать исходные значения, его не копировать в error_text без фильтрации.
Фактическое число строк, вставленных до отката внутри T3, может использоваться в описании ошибки, но не в rows_loaded. После отката зафиксировано 0.
Если ошибка произошла до начала T3, RAW-вставок ещё нет: сразу перейти к T4. Не считать ROLLBACK T4 доказательством отсутствия незавершённого T3 — порядок контекстов должен быть явным.

10. Завершение

Закрыть книгу, BytesIO и соединение в любом исходе. Сообщить load_id, конечный статус и три зафиксированных количества; секреты не печатать. SUCCESS и штатный SKIPPED — код завершения 0; FAILED или неопределённый результат — ненулевой код.
После подтверждённого SUCCESS допустима read-only сверка журнала и количества RAW-строк для load_id. Если такая последующая проверка не удалась из-за сети, не переписывать уже зафиксированный SUCCESS в FAILED.

B. РЕКОМЕНДУЕМЫЕ БИБЛИОТЕКИ

openpyxl — чтение XLSX и объектов ячеек, их типов, дат и номеров строк. Уже указан в requirements.txt (3.1.5). Не использовать режим записи и workbook.save.
psycopg 3 с binary-дистрибутивом — PostgreSQL, явные транзакции, параметры, безопасное построение идентификаторов и COPY.write_row. В requirements.txt уже есть psycopg 3.3.4 и psycopg-binary 3.3.4. Использовать API psycopg 3, а не psycopg2.extras. Наличие psycopg2 в системном Python не определяет зависимости будущего pipeline.
python-dotenv — читать env-файлы как словари, явно собрать приоритеты; уже указан в requirements.txt (1.2.1). Не выводить итоговый словарь.
Стандартная библиотека: pathlib для путей; io.BytesIO для снимка XLSX; hashlib для SHA-256; uuid для UUID v4; datetime для типизированных дат/времени; logging для кратких сообщений; math для проверки конечности дробных показателей.
pandas для этого загрузчика не нужен. Он остаётся полезным для анализа, но вывод типов из смешанной колонки Postal Code может уничтожить исходный ведущий ноль. Не строить DataFrame как обязательный промежуточный слой.
Не нужны SQLAlchemy, Alembic, оркестратор, async, connection pool, собственный CSV-сериализатор или промежуточные файлы. Текстовый протокол COPY с write_row адаптирует Python-значения, включая None, даты, UUID и Unicode. Не включать FORMAT CSV, DELIMITER или собственный NULL-маркер для этого row-by-row API; binary COPY также не требуется.
На следующем этапе сверить requirements.in с уже имеющимся requirements.txt: верхнеуровневые зависимости должны отражать выбранный загрузчик. Сейчас файлы зависимостей не менять и пакеты не устанавливать.

C. ПРАВИЛА ОБРАБОТКИ ORDERS / RETURNS / PEOPLE

Общие правила

None из действительно пустой ячейки передавать как SQL NULL. Настоящий текст пустой строки, если парсер возвращает его как строку, сохранять как пустую строку. Не превращать буквальные NA, NULL, None, nan, No или Yes в пропуски и не применять fillna. При неоднозначном представлении пустого текста будущего XLSX не угадывать значение: остановить загрузку для разбора.
Не выполнять trim, replace пробелов, изменение регистра, нормализацию Unicode, транслитерацию, сортировку, фильтрацию, дедупликацию или объединение листов. Полные дубликаты и повторяющиеся бизнес-идентификаторы сохранять как отдельные строки с разными _raw_id и исходными _source_row_number.
Типовое представление адаптировать только для совместимости с утверждёнными PostgreSQL-типами; не вычислять бизнес-показатели и не исправлять источник. Неожиданные значения, которые нельзя представить без потерь, ведут к FAILED, а не к пропуску ряда.

Orders — 24 исходных поля

Row ID и Quantity: INTEGER. Непустое значение должно быть числовым целым, не bool, в диапазоне PostgreSQL INTEGER. Если openpyxl вернул уже int, передать его; если вернул float, допускается только конечное точно целое значение. Не округлять и не обрезать дробь; не парсить произвольный текстовый бизнес-идентификатор в число. Row ID окончательно утверждён как INTEGER и не заменяет _raw_id.
Order Date и Ship Date: DATE. Передать datetime.date. datetime от Excel допустим только с нулевым временем, тогда извлечение календарной даты ничего не теряет. Ненулевое время, текстовая дата, нечисловой формат или некорректная дата — FAILED, без угадывания локали и молчаливого усечения. Использовать механизм дат Excel в openpyxl, а не собственную арифметику serial date.
Sales, Discount, Profit, Shipping Cost: DOUBLE PRECISION. Передать Python float из исходного числового значения без round и Decimal-округления. bool, текст, NaN/Infinity или иные неожиданные представления — FAILED. Длинные двоичные дробные хвосты не исправлять. NULL допустим согласно DDL.
Order ID, Ship Mode, Customer ID, Customer Name, Segment, City, State, Country, Region, Market, Product ID, Category, Sub-Category, Product Name, Order Priority: TEXT. Сохранить исходные строки без преобразований; неожиданное нетекстовое значение — ошибка контракта, а не автоматический str для всех значений.

Postal Code — отдельное правило TEXT

Читать исходную ячейку напрямую; не пропускать колонку через pandas, numpy, fillna или float-конвертацию. Если ячейка содержит строку, передать её буквально: исходный текст 05408 должен остаться 05408. В текущем файле таких текстовых ячеек 11.
Если ячейка содержит числовое целое значение, передать десятичную строку самого целого значения без суффикса .0. В текущем источнике это 9 983 ячейки; openpyxl возвращает их целыми, поэтому промежуточный float не нужен. Не выполнять сначала float(value), затем str(value).
Числовой формат Excel 00000 — метаданные отображения, а не наличие ведущего нуля в значении. Число 1040, отображаемое как 01040, загрузить как текст 1040; не применять zfill и не восстанавливать несуществующий в значении ноль. Это сохраняет утверждённое различие исходного числового значения и настоящего текста 05408. Если нужно будет хранить отображение Excel, это отдельное изменение контракта, не скрытое правило RAW.
Пустая ячейка — NULL; в проверенном файле их 41 296. Не заменять на 0, пустую строку, nan или строку None. Неожиданная дробь, дата, bool или ошибка Excel — FAILED. Если будущий парсер возвращает numeric float вместо int, не использовать его как способ восстановления кода: остановиться для проверки исходного типа/точности, а не угадывать исходную строку.

Returns — 3 исходных поля

Returned, Order ID, Region: TEXT. Сохранять Yes как Yes, не преобразовывать в BOOLEAN и не заменять колонку константой. Нынешняя уникальность Order ID и единственный Returned не являются условиями фильтрации. NULL передавать по общему правилу.

People — 2 исходных поля

Person, Region: TEXT. Сохранить внутренние U+00A0 в Andile Ihejirika, Wasswa Ahmed, Lindiwe Afolayan и диакритику в Marilène Rousseau, Vasco Magalhães. Не использовать strip/split/join, Unicode normalization и ASCII-кодирование для значений. Передавать строки через Unicode-адаптацию psycopg с UTF-8 клиентской кодировкой.
Не трактовать имена как ключи справочника, не объединять регионы, не делать вывод о будущей dimension в DWH.

D. SUCCESS / FAILED / SKIPPED И СБОИ

SUCCESS: STARTED уже зафиксирована T1; T2 сохранила хеш; T3 атомарно записала все листы, сверила ожидаемые/фактические количества и завершила журнал. finished_at задан, error_text=NULL, три счётчика отражают зафиксированные записи текущего load_id.
FAILED: после полного отката T3 новая T4 фиксирует finished_at, безопасный непустой error_text и три нуля. Старые успешные или неудачные попытки не изменяются; повтор после FAILED разрешён с новым UUID.
SKIPPED: найден SUCCESS того же SHA-256; T2 завершает новую STARTED с finished_at, тремя нулями и error_text=NULL; таблицы Orders/Returns/People не изменяются. Предыдущее успешное количество не копировать в счётчики SKIPPED.
Файл с тем же содержимым, но другим путём, даёт SKIPPED. Файл с тем же именем, но другим SHA-256 может быть новой загрузкой: старые RAW-строки не удалять; пересечение бизнес-данных разных версий в этом шаге не устранять.
Счётчики STARTED равны 0 даже во время незавершённого COPY: они отражают только зафиксированные строки. Sequence identity может иметь пропуски после ROLLBACK: значения последовательностей не обязаны откатываться; не сбрасывать их и не считать пропуски потерей RAW-строк.
При аварийном завершении процесса STARTED может остаться незавершённой. Не объявлять FAILED только по возрасту. Перед отдельным восстановлением подтвердить отсутствие работающего экземпляра и сверить журнал/RAW по load_id. При отсутствии SUCCESS и зафиксированных RAW-строк можно отдельно завершить прерванную попытку FAILED; затем новый запуск получает новый UUID. Если зафиксированные строки принадлежат STARTED/FAILED, остановиться для ручного разбора, без автоматического DELETE.
Если сеть оборвалась во время COMMIT T3, исключение клиента не доказывает откат. Переподключиться и только на чтение проверить журнал по load_id: SUCCESS означает зафиксированную загрузку, повторять COPY и менять статус на FAILED нельзя. STARTED допускает обработку FAILED только после подтверждения завершения исходной транзакции и отсутствия её зафиксированных RAW-строк. Пока результат не установлен, сообщить неопределённый исход и не повторять загрузку автоматически.
Если БД недоступна и записать T4 нельзя, не утверждать, что FAILED сохранён: вывести безопасную причину и load_id, завершиться с ошибкой; журнал может остаться STARTED. Не создавать вторую систему журналов ради этого случая.
Ошибки уникальности SUCCESS, FK и CHECK не исправлять отключением ограничений, удалением старых записей или изменением источника. После отката сообщить ошибку согласно общей схеме; неподдерживаемый конкурентный запуск требует разбора, а не усложнения pipeline блокировками.

E. PYTHON-ФАЙЛЫ ДЛЯ СЛЕДУЮЩЕГО ЭТАПА

Минимальная структура:
1) pipeline/__init__.py — пакет для запуска из корня проекта.
2) pipeline/config.py — определение корня и путей, чтение env-слоёв, проверка настроек и безопасное создание параметров соединения; не содержит секретов в исходном коде.
3) pipeline/load_raw.py — точка входа и обычные функции: снимок байтов и SHA-256, чтение/проверка листов, адаптация типов, журналирование попытки, COPY трёх листов, сверка и управление транзакциями. Контракт заголовков и типовые правила для трёх листов задаются явно в этом же модуле; отдельный framework не нужен.
Предполагаемый будущий запуск: python -m pipeline.load_raw. На этом шаге запуск и сами файлы не создаются.
Для последующей проверки реализации полезен один tests/test_raw_loader.py: сохранность текстового Postal Code 05408 и числового 1040, U+00A0/диакритики, физические номера строк, отказ при дробном INTEGER и ненулевом времени, а также сценарии отката при ошибке третьего листа и повторного SHA-256 → SKIPPED. Интеграционные проверки должны выполняться в отдельно согласованном тестовом окружении, не удалять данные sales_dwh.
Не создавать сейчас Python-файлы, SQL, migrations, новые таблицы, YAML-конфигурации и дополнительные уровни STAGING/DWH/MART. Единственный результат текущего шага — этот текстовый документ.

Основания для выбора API (официальная документация, проверена при проектировании):
- openpyxl: https://openpyxl.readthedocs.io/en/stable/api/openpyxl.reader.excel.html
  Режимы read_only/data_only и чтение файлового объекта; data_only переключает формулу на сохранённое значение, поэтому для обнаружения формул выбран False.
- psycopg COPY: https://www.psycopg.org/psycopg3/docs/basic/copy.html
  COPY поддерживает row-by-row адаптацию Python-значений и участвует в транзакции; выбран текстовый write_row без ручной CSV-сериализации.
- psycopg transactions: https://www.psycopg.org/psycopg3/docs/basic/transactions.html
  Явные транзакционные контексты позволяют отделить короткие операции журнала от атомарной RAW-загрузки.
- python-dotenv: https://bbc2.github.io/python-dotenv/
  dotenv_values позволяет собрать явные слои конфигурации без изменения окружения процесса.
