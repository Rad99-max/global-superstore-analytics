GLOBAL SUPERSTORE — MART SALES & PROFITABILITY: ДИЗАЙН

1. НАЗНАЧЕНИЕ И GRAIN

Бизнес-вопрос: «За счёт чего формируются прибыль и убытки компании и насколько
качественно растут продажи?»
Таблица: mart.sales_profitability_monthly.
Одна строка = календарный месяц Order Date + Order Profitability Status
+ Business Discount Group. Глобально по бизнесу, без Customer/Product/Geography grain.
Текущий источник: SUCCESS load_id f44edd71-d712-4fa0-81d3-98ad24e00599.
Read-only исследование sales_dwh выполнено 2026-10-18.
Ожидается 542 фактические комбинации за 48 месяцев: 2012-01-01..2015-12-01.
Ранее исследованные 862 комбинации относятся к техническим группам скидок DWH;
после бизнес-свёртки правильное ожидаемое количество — 542.

2. ПОЛЯ, ТИПЫ И КЛЮЧИ

поле | PostgreSQL тип | обязательность | назначение
month_date | DATE | NOT NULL | первое число календарного месяца Order Date
order_profitability_status | TEXT | NOT NULL | PROFITABLE / LOSS_MAKING / BREAK_EVEN
discount_group | TEXT | NOT NULL | бизнес-группа скидки, включая UNKNOWN / INVALID
sales | NUMERIC без (p,s) | NOT NULL | сумма Sales товарных строк этой комбинации
profit | NUMERIC без (p,s) | NOT NULL | сумма Profit товарных строк этой комбинации

Составной PRIMARY KEY: (month_date, order_profitability_status, discount_group).
Surrogate key не нужен. Индекс PK достаточен для маленькой месячной публикации;
дополнительные индексы сейчас не нужны. PostgreSQL ENUM не нужен.
Оправданные проверки: первое число месяца и допустимые значения двух классификаторов.
Не ограничивать Profit положительными значениями. Не требовать положительного Profit
в каждой строке со статусом PROFITABLE: статус относится к заказу, а мера — к его части.
Не вводить правила, автоматически исправляющие Sales/Profit или DQ-классы.
Не добавлять Orders, строки, идентификаторы заказов, даты отгрузки, shipping_cost,
проценты, готовые Insights или технические поля в пятиколоночный контракт MART.
Не хранить отдельно Profit Margin, Profitable Sales и Loss-Making Sales.
Year/Quarter/Month и сортировку представления хранить в семантической модели.
SQL FK month_date на dim_date не требуется: календарь проверяется при публикации,
а связь отчёта создаётся отдельно в Power BI.

3. ИСТОЧНИКИ И ПРОТИВОДЕЙСТВИЕ FAN-OUT

fact_order: order_key, total_profit для статуса, order_date_key для Order Date.
fact_order_line: order_key, sales, profit, discount_group; discount для контроля границ.
dim_date: date_key -> calendar_date -> первое число месяца.
Связь line -> order по order_key должна быть many-to-one; order -> date — many-to-one.
Каждая исходная строка должна пройти соединения ровно один раз.
После определения статуса заказа перенести его на все его строки, затем агрегировать
строки по month_date, статусу заказа и бизнес-группе скидки.
Sales = SUM(fact_order_line.sales); Profit = SUM(fact_order_line.profit).
Не переносить total_sales/total_profit заказа в каждую Discount Group.
Не распределять прибыль заказа пропорционально Sales; использовать исходный Profit строк.
Не округлять NUMERIC и не преобразовывать деньги обратно в floating point.
Не использовать Returns, People или Ship Date при построении этого MART.

В DWH 3 913 заказов имеют несколько технических discount_group;
после бизнес-свёртки несколько групп остаются у 3 638 заказов.
Значит Discount Group не является атрибутом целого заказа.
Для всех 25 739 заказов суммы Sales/Profit строк совпадают с total_sales/total_profit.
Grain позволяет суммировать Sales/Profit по любому подмножеству месяцев, статусов и групп.
Количество заказов по группам неаддитивно; этот MART не предназначен для Orders KPI.

4. PROFITABILITY LOGIC

Использовать точный NUMERIC fact_order.total_profit без округления и epsilon:
> 0 -> PROFITABLE; < 0 -> LOSS_MAKING; = 0 -> BREAK_EVEN.
NULL total_profit не превращать в BREAK_EVEN: остановить публикацию.
Не определять статус по Profit строки или суммарному Profit месяца/группы.
При фильтре скидки показывается вклад соответствующих строк, но статус заказа
остаётся определённым по полной прибыли заказа до фильтрации Discount Group.
Прибыльная строка может принадлежать LOSS_MAKING заказу и наоборот.
Часть BREAK_EVEN заказа в отдельной Discount Group может иметь ненулевой Profit;
при суммировании всех его строк Profit должен быть равен нулю.

5. BUSINESS DISCOUNT GROUPS

Техническая группа DWH | бизнес-группа | диапазон
0 | 0% | Discount = 0
(0;0.10] | 0–10% | 0 < Discount <= 0.10
(0.10;0.20] | 10–20% | 0.10 < Discount <= 0.20
(0.20;0.30] | 20–30% | 0.20 < Discount <= 0.30
(0.30;0.40], (0.40;0.50], (0.50;0.60], (0.60;0.70], (0.70;1] | 30%+ | 0.30 < Discount <= 1
UNKNOWN | UNKNOWN | неизвестная скидка, отдельно для DQ
INVALID | INVALID | недопустимая скидка, отдельно для DQ

30%+ означает строго Discount > 30%; ровно 30% относится к 20–30%.
Метки интервалов используют символ U+2013 (–); реализация должна сохранять эти метки.
Не изменять DWH discount и не округлять скидку повторно.
UNKNOWN и INVALID не исключать из общих Sales/Profit и не объединять с нормальными группами.
Для них Margin по-прежнему отношение сумм, если Sales не равен нулю.
Неожиданная техническая метка/NULL discount_group — ошибка контракта, а не новая
нормальная группа: остановить публикацию. Существующие UNKNOWN/INVALID сохранить.
Проверять соответствие меток числовой скидке: NULL -> UNKNOWN;
Discount вне [0,1] -> INVALID; остальные значения — по таблице диапазонов.
В текущем DWH UNKNOWN = 0 строк, INVALID = 0 строк.
Discount = 0.300: 340 строк в 20–30%; минимальная скидка > 0.30 — 0.320.

6. ПОЛНОТА КОМБИНАЦИЙ И ОБНОВЛЕНИЕ

Хранить только фактические комбинации, даже если их Sales/Profit в сумме равны нулю.
Не удалять группы через HAVING SUM(...) <> 0.
Полная декартова сетка Month x Status x Discount Group не нужна:
для пяти нормальных групп она дала бы 720 строк вместо текущих 542;
с UNKNOWN/INVALID — 1 008 строк, преимущественно искусственных.
Отсутствие комбинации означает отсутствие исходных строк, а не потерю публикации.
Для оси полного покрытия использовать DimDate и при необходимости Show items with no data.
Денежную аддитивную меру можно отображать как 0 для отсутствующей комбинации
только внутри подтверждённого покрытия. Margin при отсутствии Sales — BLANK.
Полностью отсутствующий месяц будущего источника проверять отдельно на полноту;
не маскировать неполную загрузку заполнением всех комбинаций нулями.
В текущем источнике все 48 месяцев содержат заказы.

Будущая загрузка: полная атомарная пересборка MART в одной транзакции,
с согласованным снимком чтения, проверками до публикации и reconciliation до COMMIT.
Не смешивать load_id и не дописывать повторно снимки. Повторный запуск должен давать
те же 542 ключа и все те же значения. При ошибке сохранять прежнюю публикацию через ROLLBACK.

7. POWER BI: DATE RELATIONSHIP И СОРТИРОВКА

DimDate[calendar_date] (1) -> SalesProfitabilityMonthly[month_date] (*):
активная связь, одно направление DimDate -> MART, обе колонки Date.
Не связывать MART с повторяющимся MonthStart календаря через many-to-many.
Не связывать month_date с integer date_key и не связывать напрямую два MART.
Для Executive Overview и этой страницы допустим один общий DimDate с отдельными
однонаправленными связями к каждому MART; не суммировать показатели двух MART вместе.
Year/Quarter/YearMonth slicers и оси брать из DimDate.
Month -> Quarter -> Year: сначала суммировать деньги, затем вычислять Margin.
YearMonth сортировать хронологически по Year*100+Month.
Дневной/недельный drill-down, отдельные дни и MTD не поддерживаются месячным grain.

Текущий dim_date: 1 468 дней, 2012-01-01..2016-01-07.
Для этих месячных страниц импортировать полный ежедневный календарь 2012-01-01..2015-12-31
(1 461 день); не включать неполный 2016 год только из-за Ship Date.
Проверить уникальные непрерывные даты без NULL и полные годы; Mark as date table,
отключить Auto date/time. Будущее расширение покрытия требует проверки календаря.

Порядок скидок: 0% -> 0–10% -> 10–20% -> 20–30% -> 30%+ -> UNKNOWN -> INVALID.
Создать в Power Query маленький справочник представления BusinessDiscountGroup
с семью уникальными метками и sort_order 1..7. Это объект модели Power BI, не новая таблица БД.
Связь справочник (1) -> MART.discount_group (*), однонаправленная.
В самом справочнике задать Sort by column: label по sort_order; sort_order скрыть.
Использовать label справочника в slicers/легендах, не алфавитную сортировку меток факта.
Так сохраняется пятиколоночная структура MART и видимость отдельных DQ-групп.
Tooltip: «Верхняя граница включена; 30%+ означает строго больше 30%».

8. KPI И VISUAL COVERAGE

Sales = SUM(sales).
Profit = SUM(profit).
Profit Margin = DIVIDE(SUM(profit), SUM(sales)); нулевой знаменатель -> BLANK.
Profitable Sales = SUM(sales) с фильтром статуса PROFITABLE.
Loss-Making Sales = SUM(sales) с фильтром статуса LOSS_MAKING.
Не хранить эти три производные меры в БД. Контракт KPI имеет фиксированный статус;
меры не должны случайно превращаться в другой KPI из-за противоречащего status slicer.
Рекомендуется не добавлять общий status slicer на первую версию страницы;
Discount и Date фильтры сохраняются в производных мерах.
Sales = Profitable Sales + Loss-Making Sales + Break-even Sales.
Break-even не исключать из Sales/Profit; третья часть может быть отдельным tooltip/пояснением.

Profitable vs Loss-Making Sales Trend: месячные Sales по двум статусам, с пояснением Break-even.
Discount Level -> Profit Margin: отношение сумм по бизнес-группам скидки.
Profit by Profitable vs Loss-Making Orders: сумма Profit строк по статусу целого заказа;
это денежный вклад, а не количество заказов. При фильтре Discount — только вклад выбранных строк.
Sales by Discount Group over Time: месячные Sales по пяти бизнес-группам;
DQ-группы видны отдельно при наличии данных и учитываются в общих итогах.
Business Insights: изменения Sales/Profit, Margin, долей продаж по статусам и скидкам.
Grain достаточен для всех пяти KPI и всех утверждённых visuals.
Если показываются YoY/PY, вычислять в DAX через DimDate при полном сопоставимом покрытии;
2012 не имеет PY. Отсутствующий/нулевой PY не подменять нулевым ростом.
Маржу и изменения в п.п. вычислять из отношений сумм, не средних процентов.
Отрицательная база Profit PY требует пояснения смены знака, а не автоматического вывода о росте.

10. КРИТЕРИИ ПРИЁМКИ БУДУЩЕЙ РЕАЛИЗАЦИИ

1) База sales_dwh; один согласованный SUCCESS load_id в обеих исходных facts.
2) Все 51 290 строк разрешаются ровно в один заказ и одну Order Date;
   _load_id и Order Date строк совпадают с заказом, обязательные меры не NULL.
3) Sales/Profit строк сверяются с каждым заказом до построения MART.
4) Статус присвоен по total_profit заказа; NULL/неизвестные статусы не замаскированы.
5) Каждая строка попадает ровно в одну бизнес-группу; границы 0, .10, .20, .30, 1,
   а также NULL и значения вне [0,1] проверены отдельными тестовыми случаями без изменения БД.
6) Все исходные строки покрыты, в том числе UNKNOWN/INVALID; нет fan-out.
7) PK уникален, поля не NULL, month_date — первое число; 542 фактические комбинации.
8) Независимо сверены каждая Month + Status + Group, месячные итоги, срезы по статусам
   и группам, квартальные/годовые итоги и точные общие NUMERIC суммы из раздела 9.
9) Суммы совпадают с fact_order после свёртки всех групп; нет повторения order totals.
10) Повторная публикация даёт идентичные ключи/значения; RAW/STAGING/DWH не меняются;
    ошибка до COMMIT откатывает всю пересборку и сохраняет предыдущий MART.
11) В Power BI проверены Date relationship, Year/Quarter slicers, сортировка скидок,
    BLANK Margin при нулевых Sales, Break-even, DQ-группы и взвешенная Margin итогов.
12) Проверен mapping PostgreSQL NUMERIC -> Power BI и допустимые расхождения отображения:
    Power BI Decimal Number приблизителен, Fixed Decimal ограничивает шкалу четырьмя.
    Не округлять PostgreSQL ради формата отчёта; DWH/MART остаются точным контролем.

542 строки — контроль текущего снимка, а не вечное ограничение размера таблицы.
