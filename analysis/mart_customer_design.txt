GLOBAL SUPERSTORE — MART CUSTOMER ANALYSIS: ДИЗАЙН

1. НАЗНАЧЕНИЕ И GRAIN

Бизнес-вопрос: «Какие клиенты создают прибыль компании, а какие создают оборот,
но в итоге приносят убыток?»
Предлагаемое имя: mart.customer_monthly.
Утверждённый grain: одна строка = Month по Order Date + Customer Key.
Customer определяется только customer_key / Customer ID, не Customer Name.
Текущий SUCCESS load_id: f44edd71-d712-4fa0-81d3-98ad24e00599.
Read-only проверка sales_dwh: 2026-10-18.
Ожидается 25 450 фактических комбинаций, 17 415 клиентов, 48 месяцев,
month_date 2012-01-01..2015-12-01.

2. ПОЛЯ, ТИПЫ И КЛЮЧИ

поле | PostgreSQL тип | обязательность | назначение
month_date | DATE | NOT NULL | первое число календарного месяца Order Date
customer_key | BIGINT | NOT NULL | ссылка на dwh.dim_customer
sales | NUMERIC без (p,s) | NOT NULL | SUM(fact_order.total_sales) клиента за месяц
profit | NUMERIC без (p,s) | NOT NULL | SUM(fact_order.total_profit) клиента за месяц

PRIMARY KEY (month_date, customer_key).
FOREIGN KEY customer_key -> dwh.dim_customer(customer_key), без ON DELETE CASCADE.
Оправдан CHECK первого числа месяца; не ограничивать знак Sales/Profit.
PK достаточен для временных выборок; отдельный customer_key индекс оправдан для FK
и клиентских фильтров. Другие индексы сейчас не нужны.
Не добавлять surrogate key MART, технические поля, имя, Segment или календарные атрибуты.
Не хранить profitability status, Customers, Profitable Customers, Unprofitable Customers,
Profit per Customer или Unprofitable Customer Rate в месячных строках MART.
Контракт содержит только четыре утверждённых поля.

3. ИСТОЧНИКИ, АДДИТИВНОСТЬ И FAN-OUT

fact_order: customer_key, total_sales, total_profit, order_date_key.
fact_order.order_date_key -> dim_date.date_key -> calendar_date -> month_date.
dim_customer: customer_id, customer_name, segment для представления и фильтрации.
Группировать заказы по month_date и customer_key; деньги SUM без округления или float.
Считать из fact_order без присоединения товарных строк и без классификации заказов.
Не переносить order profitability на клиента: клиент может иметь заказы разных знаков.
Проверять, что каждый заказ разрешается в одного клиента и одну дату, без fan-out.
Текущая проверка: 25 739 строк соединения = 25 739 уникальных order_key;
orphan/NULL проверенных дат, клиентов и денежных мер = 0.

Sales и Profit аддитивны Month -> Quarter -> Year и по уникальным customer_key.
При объединении месяцев сначала суммировать Profit одного клиента за весь набор,
затем классифицировать; не суммировать результаты месячных классификаций.
Месячный grain достаточен для одного/нескольких полных месяцев, кварталов и лет,
включая непоследовательный набор выбранных месяцев. Не заменять такой набор диапазоном
MIN..MAX: это незаметно добавит невыбранные месяцы.

4. CUSTOMER STATUS И АКТИВНОСТЬ

В текущем filter context (период + Customer Segment + допустимые клиентские фильтры):
1) Получить уникальные customer_key, имеющие фактические строки MART в этом периоде.
2) Для каждого активного клиента вычислить SUM(profit) по всем выбранным месяцам.
3) > 0 -> PROFITABLE; < 0 -> UNPROFITABLE; = 0 -> BREAK_EVEN.
4) Только после этого считать клиентов по статусам и производные KPI.
Не использовать статический атрибут dimension, calculated column или фиксированную
calculated table, пересчитываемую только при refresh, для динамического статуса.
Не определять статус по отдельному заказу или месяцу при выборе нескольких месяцев.

Активность определяется наличием строки MART, не Sales > 0 и не Profit <> 0.
Клиент с заказами и итоговым Profit = 0 активен и является BREAK_EVEN.
Клиент без строк в выбранном периоде не входит ни в Customers, ни в одну когорту.
Не превращать BLANK отсутствующей активности в 0 до определения активных клиентов.
Не считать всех клиентов из dim_customer: однонаправленная дата не фильтрует dimension
обратно через MART. Использовать distinct customer_key факта в нужном контексте.
При итерации по этому набору явно применять фильтр текущего customer_key/переход
контекста, чтобы каждый клиент получил собственный Profit, а не общий Profit страницы.

Customers = число уникальных активных клиентов.
Profitable Customers = число активных клиентов с Profit выбранного периода > 0.
Unprofitable Customers = число активных клиентов с Profit выбранного периода < 0.
Profit per Customer = SUM(profit) / Customers.
Unprofitable Customer Rate = Unprofitable Customers / Customers.
Для отношений использовать DIVIDE, нулевой знаменатель -> BLANK.
Customers = Profitable + Unprofitable + Break-even Customers.
Клиентские количества неаддитивны по времени; на квартале/годе/итоге пересчитывать
distinct-набор и статусы. Нельзя суммировать месячные количества или усреднять ставки.
При отсутствии активности счётчики для карточек допустимо отображать как 0;
отношения сохраняют BLANK. Это правило отображения, не создание нулевых строк MART.

5. ФИКСИРОВАННЫЕ КОГОРТЫ ДЛЯ PROFIT TREND

Состав когорт определяется внешним выбранным периодом целиком и сохраняется
во всех точках месячного тренда; он меняется только при изменении выбора пользователя.
Концептуальная DAX-последовательность, без готовой реализации:
1) До итерации по клиентам сохранить набор выбранных дат через ALLSELECTED(DimDate).
   Убрать влияние текущего Month/YearMonth оси, сохранив Year/Quarter slicers и внешние
   фильтры. Использовать весь календарь, а не только calendar_date при оси YearMonth.
2) Снять текущие фильтры DimDate при расчёте периода когорты и наложить сохранённый
   набор выбранных дат. Сохранить фильтры DimCustomer, включая Segment.
3) В этом контексте получить активных клиентов ВСЕГО выбранного периода,
   а не только текущей точки тренда.
4) Посчитать Profit каждого такого клиента в выбранном периоде и сформировать
   три непересекающихся уникальных набора customer_key по знаку Profit.
5) Для значения точки вернуть исходный месячный контекст оси и суммировать Profit
   только клиентов нужного набора, применяя набор ключей к DimCustomer/MART.
   Не снимать фильтр месяца при вычислении самого месячного значения.
6) Наборы ключей не размножать соединением; использовать фильтрацию уникальными ключами.

ALLSELECTED подходит для простого визуала с осью DimDate и внешними Year/Quarter slicers.
Сохранить выбранные даты в переменной вне клиентской итерации; не вызывать ALLSELECTED
глубоко внутри вложенных итераторов, где результат может зависеть от промежуточного контекста.
CALCULATE/CALCULATETABLE управляют фильтром периода и переходом контекста клиента.
Если будущие visual interactions меняют смысл внешнего выбора, сначала проверить
поведение ALLSELECTED; отдельный disconnected period selector возможен только после
такой потребности и отдельного согласования, сейчас он не нужен.

Клиент PROFITABLE когорты может иметь отрицательный месячный Profit; он остаётся
в той же когорте. Аналогично клиент BREAK_EVEN когорты может иметь месяцы разных знаков.
Клиент без активности в точке не вносит месячный Profit, но не покидает когорту.
Отсутствующий месячный вклад допустимо отобразить как 0 внутри покрытия.
Сумма Profit трёх когорт в каждом месяце должна совпадать с общим Profit месяца
для выбранного Segment/периода; сумма тренда когорты — с Profit этой когорты за период.
Обычные KPI в текущем контексте и fixed-cohort trend — разные контекстные меры:
месячную переклассификацию KPI нельзя использовать для легенды фиксированного тренда.

6. POWER BI RELATIONSHIPS И SEGMENT

DimDate[calendar_date] (1) -> CustomerMonthly[month_date] (*), активная.
DimCustomer[customer_key] (1) -> CustomerMonthly[customer_key] (*), активная.
Фильтрация только от dimensions к MART, без many-to-many и bidirectional.
Не связывать MART по имени клиента или Segment. Customer Name может повторяться.
Year/Quarter slicers и YearMonth ось — из DimDate; Segment — из DimCustomer.
Segment однозначен для customer_key; текущие NULL Segment = 0.
Consumer: 8 987; Corporate: 5 221; Home Office: 3 207 клиентов.
Изменения Segment во времени не моделируются текущим DWH: используется опубликованный
атрибут клиента. Историческую SCD-логику не добавлять без отдельного требования.

Обе даты имеют тип Date; month_date — первое число месяца.
Не связывать с повторяющимся MonthStart или integer date_key.
Для текущих месячных страниц использовать полный ежедневный DimDate
2012-01-01..2015-12-31 (1 461 день); Mark as date table, Auto date/time отключить.
Январь 2016 в DWH обусловлен Ship Date и не расширяет покрытие этого MART.
Дневные slicers, MTD и недельный drill-down месячный grain не поддерживает.
Не связывать MART напрямую с другими MART и не ожидать, что Segment автоматически
фильтрует глобальные публикации без customer grain.

7. ОТСУТСТВУЮЩИЕ И НУЛЕВЫЕ КОМБИНАЦИИ

Полная Month x Customer сетка не нужна: 48 x 17 415 = 835 920 строк
против 25 450 фактических. Искусственные строки сделали бы неактивных клиентов активными.
Хранить только комбинации с заказами, но сохранять их независимо от знака и нуля сумм.
Не использовать HAVING SUM(profit) <> 0 или фильтр Sales > 0.
В текущем DWH 159 Month + Customer имеют Profit = 0; все имеют реальные заказы.
Из них Sales = 0 и Profit = 0 одновременно: 0; это факт текущих данных, не ограничение.
Пример: customer_key 15118, январь 2012, Sales = 5.9399999999999995, Profit = 0,
один заказ. Этот клиент активен в январе и должен учитываться в январской классификации.
В январе 2012 всего 215 активных клиентов; 17 200 остальных не являются Break-even.
Каждый клиент имеет месяцы без заказов; активность текущих клиентов — от 1 до 8 месяцев.
Текущие 1 570 клиентов имеют месяцы обоих знаков Profit, 1 191 — годы обоих знаков.
Не трактовать отсутствующие месяцы как наблюдаемый Profit = 0 при анализе смены знака.

фиксированный SUCCESS load_id, без смешивания версий. Ошибка -> ROLLBACK,
предыдущая публикация сохранена. Повторная загрузка даёт идентичные ключи и значения.
RAW/STAGING/DWH не менять. Технический журнал не добавлять полями в этот MART.
